# Модуль 1. Введение в Apache Kafka

> 2 ак.ч · ~1 час теория + ~1 час live coding

## Цели модуля

- Развернуть локальный стенд Kafka + ZooKeeper + Kafdrop через Docker Compose.
- Понять модель данных Kafka: сообщения, топики, партиции, репликация, офсеты.
- Разобраться в гарантиях доставки и в том, какие API есть у Kafka.
- Научиться работать с топиками и сообщениями через CLI и наблюдать их в Kafdrop.

---

## 1. Что такое Kafka и зачем она разработчику

Apache Kafka — это распределённый, реплицируемый, устойчивый к сбоям
**лог событий** (event streaming platform). Разработчик воспринимает Kafka как
набор **топиков** (именованных очередей/логов), в которые продюсеры пишут
сообщения, а консюмеры их читают.

Ключевые свойства:
- **append-only лог** — сообщения только дописываются, не изменяются и не
  удаляются «по месту» (удаление — только по политике хранения/retention).
- **персистентность** — данные пишутся на диск и переживают рестарт брокера.
- **масштабируемость** — партиции распределяются по брокерам, чтение и запись
  идут параллельно.
- **отказоустойчивость** — каждая партиция реплицируется на несколько брокеров.

Типовые сценарии использования: шина событий между сервисами, потоковая
обработка, изменение-данных (CDC), стриминг аналитики, источник для ML.

---

## 2. Роли: ZooKeeper и Kafka (режимы координации)

Kafka долгое время использовала **ZooKeeper** для хранения метаданных кластера
(список брокеров, лидеры партиций, конфигурации). Начиная с Kafka 3.x появился
режим **KRaft** (Kafka Raft), который убирает внешний ZooKeeper и хранит
метаданные внутри самих брокеров/контроллеров. В **Kafka 4.x ZooKeeper удалён
полностью** — остался только KRaft.

В этом курсе мы используем классический режим **ZooKeeper** (образы Confluent
`cp-zookeeper` + `cp-kafka`): он нагляден для обучения и совместим с Kafdrop.

| | ZooKeeper-режим (этот курс) | KRaft (Kafka 4.x) |
|---|---|---|
| Координация | внешний ZooKeeper | внутри Kafka (Raft-кворум) |
| Компоненты | 1 ZooKeeper + N брокеров | N брокеров/контроллеров |
| Удобство | классика, много доков | проще эксплуатация, меньше узлов |

## 3. Сообщения и топики

**Сообщение (record)** — минимальная единица данных. Состоит из:

| Поле | Описание | Обязательно |
|---|---|---|
| `key` | необязательный ключ; влияет на партицию | нет |
| `value` | полезная нагрузка (байты) | да |
| `timestamp` | время создания (create/log-append) | неявно |
| `headers` | произвольные пары ключ-значение | нет |
| `offset` | позиция сообщения в партиции (назначает Kafka) | — |

**Топик (topic)** — именованный лог, в который пишут продюсеры и из которого
читают консюмеры. Топик логически делится на **партиции**.

Важно: Kafka хранит сообщения как **байты** (`byte[]`). Сериализация
(JSON/Avro/Protobuf) — зона ответственности клиента (см. Модуль 7).

---

## 4. Партиции

**Партиция (partition)** — единица параллелизма и распределения данных. Топик
состоит из 1..N партиций; каждая партиция — это упорядоченный, неизменяемый
лог с собственными офсетами.

- **Порядок гарантируется только внутри одной партиции**, не между партициями.
- Сообщение попадает в конкретную партицию по правилу:
  - если задан `key` → `partition = hash(key) % num_partitions`;
  - если ключа нет → round-robin (в новых версиях — sticky, «липкий» батчинг).
- Больше партиций → больше параллелизма, но и больше накладных расходов.
  Один консюмер в группе может читать несколько партиций, но одна партиция
  отдаётся только одному консюмеру группы (см. Модуль 3).

**Офсет (offset)** — монотонно возрастающий номер сообщения внутри партиции.
Консюмер использует офсет для «закладки»: откуда читать дальше.

---

## 5. Репликация

Для отказоустойчивости каждая партиция имеет **реплики**:

- **leader** — реплика, обслуживающая все чтения и записи;
- **followers** — пассивные копии, синхронизирующиеся с лидером.

Параметры:
- `replication.factor` (RF) — сколько копий партиции. Типовое значение **3**.
- **ISR** (in-sync replicas) — реплики, которые не отстали от лидера.
- `min.insync.replicas` — сколько реплик обязаны подтвердить запись, чтобы она
  считалась успешной. Схема `RF=3, min.insync.replicas=2` выдерживает отказ
  одной ноды.

Если лидер падает, Kafka выбирает нового лидера из ISR. Если реплика отстала и
выбыла из ISR, она не может стать лидером без риска потери данных.

> В нашем локальном стенде **три брокера** (kafka1..kafka3), поэтому реально
> работает `replication.factor=3` и `min.insync.replicas=2`. Переключение лидера
> демонстрируется в live coding ниже (шаг «Failover»).

---

## 6. Гарантии (доставка и хранение)

Гарантии Kafka:
- **Сообщение, подтверждённое продюсеру при `acks=all`, не будет потеряно** при
  отказе ≤ (RF − min.insync.replicas) брокеров.
- **Сообщения в партиции читаются в порядке офсетов**.
- **Консюмер читает каждое сообщение хотя бы один раз** при правильной
  настройке коммитов (at-least-once).

Три уровня семантики доставки (подробно в Модуле 5):
- **at-most-once** — можно потерять, дублей нет;
- **at-least-once** — дубли возможны, потерь нет (дефолт);
- **exactly-once** — ни потерь, ни дублей (идемпотентный продюсер +
  транзакции / Kafka Streams EOS).

Хранение: Kafka хранит данные `log.retention.hours` (или по размеру) и
удаляет старые сегменты. **Офсет не сбрасывается** при удалении данных —
консюмер, читающий «с конца», просто не увидит старые сообщения.

## 7. API Kafka

| API | Класс / инструмент | Для чего |
|---|---|---|
| **Producer API** | `KafkaProducer` | запись сообщений (Модуль 2) |
| **Consumer API** | `KafkaConsumer` | чтение сообщений (Модуль 3) |
| **Admin API** | `AdminClient` | управление топиками/ACL/квотами (Модуль 4) |
| **Streams API** | `KafkaStreams` | потоковая обработка (Модуль 6) |
| **Connect API** | Kafka Connect | интеграции с БД/хранилищами (вне рамок этого курса) |
| **REST API** | Confluent REST Proxy | HTTP-доступ к Kafka (Модуль 8) |
| **CLI** | `kafka-topics`, `kafka-console-*` | ручное администрирование |

## Live coding: «Настройка кластера Kafka»

### Шаг 1. Поднимаем стенд

```bash
# Откройте терминал в папке курса (там, где лежит docker-compose.yml)
docker compose up -d
docker compose ps
```

Ожидаем, что поднялись все сервисы: `zookeeper`, `kafka1`, `kafka2`, `kafka3`
(healthy), `kafdrop`, `schema-registry`, `rest-proxy` и Flink
(`flink-jobmanager`, `flink-taskmanager`).

> Flink понадобится только в Модуле 9 — в Модуле 1 его можно не трогать.

### Шаг 2. Проверяем ZooKeeper и брокера

```bash
# ZooKeeper жив (4lw-команда `srvr` разрешена по умолчанию)
docker exec kafka-zookeeper bash -c "echo srvr | nc localhost 2181"

# Версия и ID брокера
docker exec kafka1 kafka-broker-api-versions --bootstrap-server localhost:29092 | head -5

# Пока топиков нет (автосоздание отключено)
docker exec kafka1 kafka-topics --bootstrap-server localhost:29092 --list
```

### Шаг 3. Создаём топик `orders`

```bash
# 3 партиции, RF=3 (реплики на трёх брокерах)
docker exec kafka1 kafka-topics --bootstrap-server localhost:29092 \
  --create --topic orders --partitions 3 --replication-factor 3

docker exec kafka1 kafka-topics --bootstrap-server localhost:29092 \
  --describe --topic orders
```

Разбираем вывод `--describe`:

```
Topic: orders   TopicId: ...   PartitionCount: 3   ReplicationFactor: 3
  Partition: 0  Leader: 2  Replicas: 2,1,3  Isr: 2,1,3
  Partition: 1  Leader: 1  Replicas: 1,3,2  Isr: 1,3,2
  Partition: 2  Leader: 3  Replicas: 3,2,1  Isr: 3,2,1
```

- `ReplicationFactor: 3` — у каждой партиции три копии.
- `Replicas: 2,1,3` — список брокеров-реплик (первый — предпочтительный лидер).
- `Leader` **распределён** по брокерам 1/2/3 (не все у одного).
- `Isr` — реплики, синхронные с лидером.

### Шаг 4. Пишем сообщения через console-producer

```bash
docker exec -it kafka1 kafka-console-producer \
  --bootstrap-server localhost:29092 --topic orders
```

Введите построчно несколько сообщений (Enter после каждого, Ctrl+C для выхода):

```
{"orderId": "1001", "status": "NEW"}
{"orderId": "1002", "status": "PAID"}
{"orderId": "1003", "status": "NEW"}
```

### Шаг 5. Читаем через console-consumer

```bash
docker exec -it kafka1 kafka-console-consumer \
  --bootstrap-server localhost:29092 --topic orders --from-beginning
```

`--from-beginning` читает с offset 0; без него — только новые сообщения.

### Шаг 6. Партиции и ключи

Посмотрим, как ключ определяет партицию. Создадим сообщения с ключами:

```bash
docker exec -it kafka1 kafka-console-producer \
  --bootstrap-server localhost:29092 --topic orders \
  --property "parse.key=true" --property "key.separator=:"
```

Введите (ключ:значение):

```
1001:{"orderId":"1001","status":"NEW"}
1002:{"orderId":"1002","status":"PAID"}
```

Проверим распределение по партициям (вывод покажет `Partition: N` для каждого):

```bash
docker exec kafka1 kafka-console-consumer \
  --bootstrap-server localhost:29092 --topic orders --from-beginning \
  --property print.key=true --property print.partition=true
```

Один и тот же ключ всегда попадает в одну партицию — поэтому сообщения с одним
`orderId` обрабатываются в порядке записи.

### Шаг 7. Наблюдаем в Kafdrop

Откройте <http://localhost:9000>. Проверьте:
- вкладка **Topics** → `orders` → список партиций, лидер, офсеты;
- вкладка **Consumers** (появится после запуска консюмера в Модуле 3);
- вкладка **Brokers** — три брокера (id=1, 2, 3).

### Шаг 8. Failover: останавливаем брокер

Остановим `kafka2` и посмотрим, что кластер выживает (лидеры партиций переезжают
на другие брокеры):

```bash
docker stop kafka2
docker exec kafka1 kafka-topics --bootstrap-server localhost:29092 --describe --topic orders
```

В `--describe` видно, что у партиций, где лидером был `kafka2`, появился новый
лидер (из `Isr`). Кластер продолжает принимать записи и отдавать их. Вернём брокер:

```bash
docker start kafka2
docker exec kafka1 kafka-topics --bootstrap-server localhost:29092 --describe --topic orders
```

### Шаг 9. Очистка

```bash
docker exec kafka1 kafka-topics --bootstrap-server localhost:29092 \
  --delete --topic orders
docker compose down -v   # полный сброс стенда (удаляет данные)
```
